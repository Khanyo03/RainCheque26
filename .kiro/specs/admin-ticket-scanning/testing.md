# Test Plan — Admin Ticket Scanning & Check-In

## 1. Role and access tests

| Scenario | Expected result |
|---|---|
| Unauthenticated user calls scanner API | 401 |
| Authenticated customer calls scan endpoint | 403 |
| Customer navigates directly to scanner route | Redirect/forbidden UI |
| Event Admin scans an event they manage | Allowed |
| Event Admin scans an event they do not manage | 403 |
| Admin requests another event's attendance history | 403 |

## 2. Ticket validation tests

| Scenario | Expected result |
|---|---|
| Valid eligible ticket for selected event | Check-in succeeds |
| Malformed QR payload | Invalid ticket |
| Unknown token | Invalid ticket |
| Ticket belongs to another event | Wrong event |
| Ticket already checked in | Already checked in |
| Cancelled ticket | Cancelled |
| Refunded ticket | Refunded, if applicable |
| Payment not confirmed | Payment not confirmed |
| Ticket ineligible under existing rules | Rejected with safe reason |

## 3. Concurrency tests
- Submit two simultaneous scan requests for the same ticket.
- Verify at most one request creates a successful check-in.
- Verify the other request receives `ALREADY_CHECKED_IN`.
- Verify exactly one check-in record exists.
- Verify retries do not create additional check-ins.

## 4. Audit tests
- Successful check-in records authenticated admin ID.
- Timestamp is generated by backend in UTC.
- Raw QR payload is not written to logs.
- JWT and secrets are not logged.
- Admin cannot set check-in timestamp or checked-in-by identity through request fields.

## 5. Frontend tests
- Scanner route is protected.
- Camera starts only after explicit admin action.
- Permission-denied state is displayed.
- Missing-camera state is displayed.
- Camera stops when component unmounts.
- Repeated QR detections do not flood the API.
- Valid and rejected outcomes are clearly and accessibly announced.
- Attendance summary refreshes after successful check-in.

## 6. Regression tests
- Customer can still view their issued QR ticket.
- Ticket purchase and payment flows still work.
- Event Admin can still manage events.
- Existing authentication and JWT flows still work.
- Existing event details and booking routes remain unchanged.

## 7. Manual end-to-end rehearsal
1. Create a test event.
2. Assign an Event Admin to manage it.
3. Create or purchase an eligible test ticket.
4. Sign in as the Event Admin and open the scanner.
5. Scan the customer's QR code.
6. Confirm successful check-in and attendance count increment.
7. Scan the same QR again and confirm duplicate rejection.
8. Scan a ticket for another event and confirm rejection.
9. Sign in as a customer and try to access the scanner and scan endpoint.
10. Confirm customer access is denied.
11. Verify check-in history contains correct admin and server timestamp.
12. Confirm customer can still display their ticket.

Use test accounts, test events and test tickets. Never use real customer tickets for destructive testing.
